MASTER PROMPT: Build EduSpark-Quiz — Complete Educational Quiz Platform

1. ROLE AND OBJECTIVE

Act as a senior full-stack developer, UI/UX designer, database architect, security engineer, and education technology product manager.

Build a complete, production-oriented educational quiz application named EduSpark-Quiz.

The application must be a real, functional product, not just a UI prototype, static website, landing page, or collection of non-working buttons.

The platform should help Indian students learn through quizzes, chapter-wise practice, mock tests, explanations, progress tracking, and competitive examination preparation.

Primary users:

- School students from Classes 6–12.
- Students preparing for SSC, Railway, Police, CET, and other competitive examinations.
- Teachers and quiz creators.
- Administrators managing educational content.

Default language: Hindi.
Additional language: English.
Target experience: Mobile-first, Android-friendly, fast, accessible, and responsive.

2. TECHNOLOGY STACK

First inspect the existing project and preserve its working architecture wherever practical.

Preferred stack:

- Frontend: React + TypeScript.
- Build tool: Vite.
- Styling: Tailwind CSS or the styling system already used by the repository.
- UI: Reusable components with accessible controls.
- Backend: Firebase.
- Authentication: Firebase Authentication.
- Database: Cloud Firestore.
- File storage: Firebase Storage, only when needed.
- Server-side privileged operations: Firebase Cloud Functions or another secure backend.
- Testing: Vitest and React Testing Library.
- End-to-end testing: Playwright where supported.
- Version control: Git and GitHub.
- Deployment: Firebase Hosting or another compatible static hosting platform.

If the existing repository uses a different framework, evaluate it before changing anything. Do not unnecessarily rewrite a working project.

Never expose Firebase Admin credentials, service account keys, private API keys, or privileged secrets in client-side code.

If Firebase configuration is missing, create a documented setup template and clear instructions. Do not fabricate credentials or claim that Firebase is connected when it is not.

9. SCORING AND RESULTS

Calculate results accurately.

For a simple quiz with one mark per correct answer and no negative marking:

Score = Number of correct answers × Marks per correct answer.

Support configurable scoring rules, including negative marking.

The result screen must show:

- Total questions.
- Attempted questions.
- Correct answers.
- Incorrect answers.
- Unanswered questions.
- Total score.
- Maximum possible score.
- Percentage.
- Time taken.
- Subject-wise performance.
- Review of answers.
- Explanations, when enabled.
- Retry Quiz.
- Return to Dashboard.

Percentage must use the maximum possible score when that definition is applicable. Handle zero or invalid maximum scores safely.

Store completed attempts so users can view their previous results.

Do not allow the client to submit an arbitrary score as the authoritative result. Validate answers and scoring on a trusted backend for competitive or high-stakes tests.

14. FIRESTORE SECURITY RULES

Create and document production-oriented Firestore Security Rules.

Requirements:

- Users may read and update only permitted fields of their own profiles.
- Users cannot edit their own role, verified score, administrative privileges, or protected statistics.
- Users cannot read another user's private profile or attempts without an explicit authorized reason.
- Quiz drafts are accessible only to authorized content managers.
- Published quiz content is readable according to its access policy.
- Correct answers must not be exposed prematurely.
- Attempts must be tied to the authenticated user.
- Sensitive scores and leaderboard records must be validated by trusted code.
- Administrative writes require verified authorization.
- Reports and audit logs must be protected.
- Default to deny when no rule explicitly grants access.

Provide a complete firestore.rules file and emulator tests for both allowed and denied operations.

Do not use open public write rules or unrestricted production access rules.
